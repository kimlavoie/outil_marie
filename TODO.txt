MIGRATION VITE + REACT + TYPESCRIPT — PLAN PAR ÉTAPES
======================================================

Contexte : une tentative précédente de migration "big bang" (tout réécrit
d'un coup) a échoué. Ce plan est conçu pour qu'à CHAQUE commit sur main,
l'app reste 100% fonctionnelle. L'app doit continuer d'être servie depuis
la racine (hébergement type GitHub Pages / Netlify).
Précision (voir "Déploiement" plus bas) : hébergée sur l'URL par défaut
GitHub Pages (kimlavoie.github.io/outil_marie/), donc dans le sous-dossier
/outil_marie/, pas la racine du domaine — `base` dans vite.config.js est
réglé en conséquence.

Notes opérationnelles
---------------------
- Un serveur statique générique (Live Server ou équivalent) ne peut plus
  être pointé sur la racine du projet source une fois du vrai TypeScript
  introduit (Phase 2) : il ne transpile rien et ne connaît pas le bon type
  MIME pour .ts (souvent mappé à video/mp2t). Pour un aperçu "sans build
  step", pointez-le sur dist/ après `npm run build`. Pour le développement
  courant, `npm run dev` (Vite) reste la bonne option — il fait déjà du
  rechargement à chaud.

Principes directeurs
---------------------
- Une PR = un module ou une vue, jamais "tout en même temps".
- Après chaque étape : `npm test` vert + checklist de smoke-test manuel
  sur les vues touchées avant de merger.
- La logique métier (state.js, db-utils.js, validation.js, fuzzy-match.js,
  backup.js) n'est JAMAIS réécrite pendant la migration — seule la couche
  de rendu DOM devient React, un morceau à la fois.
- Aucune branche "v2" qui vit des semaines en parallèle : chaque étape
  atterrit vite sur main.

    transpilation runtime). moduleResolution: "bundler",
    allowImportingTsExtensions: true (les imports gardent l'extension

[x] Renommer en .ts les modules les plus "feuilles" (peu de dépendants) en

    fuzzy-match.js (2), db-utils.js (2), validation.js (3), logger.js (5),
    utils.js (6, avec 29 exports bridgés sur window — le plus gros morceau).
    Pour chaque fichier : renommage (git mv), mise à jour de l'extension
    dans le <script type="module"> d'index.html, et mise à jour de chaque
    import qui le référence (source + tests) de ".js" vers ".ts" — mécanique,
    aucune logique touchée.
[x] Un fichier renommé = un point de validation : npx tsc, node --test,
    npm run lint, vite build (diff dist/ + vérif 200 sur chaque asset),
    vite dev, à chaque étape avant de passer au fichier suivant.
    Piège découvert : renommer en .ts active le type-check *complet* du
    fichier (contrairement aux .js où checkJs:false s'applique) — a exigé
    quelques correctifs typés minimes et sans changement de comportement
    dans utils.ts (isNaN(x) -> isNaN(Number(x)), soustraction de Date via
    .getTime(), un cast `as HTMLElement[]` localisé sur un
    querySelectorAll issu d'un paramètre non typé).
    Piège découvert : les ponts `window.X = X` (pour les scripts non-module
    qui lisent ces exports comme globals) ne sont pas connus de TypeScript.
    Centralisés dans js/globals.d.ts (déclarations `declare global`), qui
    sert aussi de manifeste de tout ce qui reste à éliminer en Phase 4-5.

    (majuscule) — collision de casse avec "dashboard.js" sur un système

    résolution de module TypeScript. Renommé en dashboard-view.tsx
    (kebab-case, cohérent avec le reste du projet).
    Piège découvert : Node sait exécuter du .ts nativement (type-stripping)
    mais PAS du .tsx (JSX exige une vraie transformation, pas juste un
    effacement de types) — donc rien d'accessible depuis le graphe
    d'import d'un fichier de test ne peut être un .tsx. dashboard.js a été
    séparé en deux : dashboard.js garde uniquement computeDashboardStats
    (pur, testé via node --test), dashboard-view.tsx porte le rendu React
    ET le pont window.renderDashboard/renderDashboardCharts (au lieu de
    faire transiter ce pont par dashboard.js, qui aurait réintroduit une
    dépendance transitive vers le .tsx dans le graphe de test).
