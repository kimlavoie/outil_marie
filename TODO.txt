=======================================================
CONTROLE UTILISATEUR SUR LES DONNEES (priorite produit)
=======================================================

Principe directeur : l'utilisateur souhaite garder le plus de controle
possible sur ses donnees. Plusieurs champs sont aujourd'hui calcules
automatiquement (tarifs, taux, taxes, totaux, dates fiscales) sans
possibilite de correction manuelle. Il serait utile d'ajouter, la ou
c'est pertinent, un mecanisme d'"exception" (surcharge manuelle) qui
laisse la valeur calculee par defaut mais permet a l'utilisateur de la
remplacer explicitement quand la situation reelle diverge de la regle
generale.

Note : les tarifs de salle ("Montant personnalise..." dans
reservations/tariff.ts), les taux de salaire/supplementaire et les
taux de service/equipement (champs "custom-rate-input" dans
reservations/subrows.ts) supportent deja une surcharge manuelle -
retires de cette liste apres verification du code.

[X] Taxes (TPS 5% / TVQ 9,975%)
    Fichier : src/activities/financial-summary.ts
    (updateSubmissionFinancialSummary, computeActivityFinancials)
    Taux fixes appliques sur le sous-total. Certaines activites
    (organismes exoneres, ententes particulieres) auraient besoin
    d'un taux ou d'un montant de taxes different, voire d'une
    exoneration complete.

[ ] Annee fiscale / numero de trimestre
    Fichier : src/state/date-helpers.ts (getFiscalYear,
    getQuarterNumber)
    Derives automatiquement de la date de debut. Pour des corrections
    comptables historiques, pouvoir forcer l'annee/trimestre sans
    changer la date reelle de l'activite serait utile.

[ ] Nombre de jours (dayCount)
    Fichiers : src/state/migrations.ts (calculateDaysCount),
    src/utils/format.ts
    Genere automatiquement a partir de date_start/date_end ; une plage
    inversee retombe a 0 puis est forcee a 1. Une surcharge manuelle
    permettrait de corriger le nombre de jours factures sans devoir
    modifier les dates elles-memes pour obtenir le bon compte.

[ ] Resolution du tarif de salle (tariff_id, tariff_description,
    tariff_gl_account_code)
    Fichiers : src/activities/reservations/index.ts (resolution de
    grille), src/state/migrations.ts
    L'id du tarif, sa description et le code de compte GL sont
    resolus automatiquement selon salle + parametre + type de client
    (ou lors de la migration heritage). Une exception permettrait de
    pointer une reservation vers un autre compte GL ou de corriger la
    resolution apres qu'une grille tarifaire ait change retroactivement.

Remarque : il faudra decider, pour chaque champ, si l'exception se
manifeste comme un simple champ modifiable qui memorise "valeur
calculee vs valeur forcee" (avec un indicateur visuel du type
"surcharge manuelle") ou comme un champ separe optionnel. A determiner
avec l'utilisateur au cas par cas avant l'implementation, plutot que
d'appliquer un patron unique partout.
