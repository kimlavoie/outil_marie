================================================================================
          PROPOSITIONS D'AMÉLIORATION - OUTIL DE GESTION DE MARIE
================================================================================

Voici une liste d'améliorations proposées pour l'application, classées par catégorie. Ces points visent à améliorer la qualité du code, la stabilité, la performance et la couverture de tests de l'application.

--------------------------------------------------------------------------------
1. QUALITÉ DU CODE
--------------------------------------------------------------------------------
[x] Découpage de js/activities.js
    - Problème : Ce fichier fait à lui seul 3401 lignes (plus que tout le reste du projet combiné), ce qui rend les modifications risquées et les régressions difficiles à repérer.
    - Solution : Scindé en 5 fichiers par domaine (activities-render.js, activities-form.js, activities-reservations.js, activities-financials.js, activities-history.js), toujours en scope global partagé via <script>. Aucune fonction déplacée n'a changé de comportement ; lint et suite de tests passent après le découpage.

[x] Généraliser l'échappement HTML des champs texte libre
    - Problème : escapeHtml() n'était utilisé qu'à 4 endroits alors qu'il y a une centaine d'assignations innerHTML = `...` avec interpolation. Plusieurs panneaux/popovers injectaient des champs libres (nom de client, notes, responsable, salle, description) sans échappement.
    - Solution : escapeHtml() déplacé dans utils.js (partagé), et appliqué systématiquement dans calendar.js, reconciliation.js, account-report.js, settings.js, navigation.js, et les 5 fichiers activities-*.js (texte, attributs value="" et title="").

[x] Ajouter un gestionnaire d'erreurs global
    - Problème : Il n'y avait aucun window.onerror ni écouteur unhandledrejection. Une erreur JS non interceptée dans un handler d'événement échouait silencieusement.
    - Solution : Ajouté dans main.js : window.addEventListener("error"/"unhandledrejection") logue en console et affiche un toast d'erreur générique.

--------------------------------------------------------------------------------
2. STABILITÉ
--------------------------------------------------------------------------------
[x] Feedback visuel en cas d'échec de sauvegarde
    - Problème : saveDatabase() était asynchrone mais appelée sans await à la plupart des endroits ; en cas d'échec IndexedDB, l'erreur n'était que loguée en console, sans que l'utilisateur en soit informé.
    - Solution : saveDatabase() (state.js) affiche maintenant un toast d'échec (une seule fois tant que les sauvegardes échouent, pour ne pas spammer) et un toast de reprise une fois la sauvegarde redevenue fonctionnelle.

[x] Validation de schéma au chargement des données
    - Problème : Aucune vérification de structure n'était faite sur appState.activities au chargement ; des données corrompues auraient pu planter l'app (ex: act.name.toLowerCase() sur une entrée sans nom).
    - Solution : Ajout de sanitizeActivitiesList() (state.js), appelée au chargement : élimine les entrées non récupérables (sans id) et corrige les champs/tableaux manquants (name, responsable, distributions, reservations) avec des valeurs par défaut sûres.

--------------------------------------------------------------------------------
3. PERFORMANCE
--------------------------------------------------------------------------------
[ ] Surveiller le coût du rendu du tableau d'activités à grande échelle
    - Problème : renderActivitiesTable() refait un filter + sort complet sur toutes les activités à chaque frappe/tri, avec des clones JSON fréquents pour les snapshots d'annulation. Pas de problème à l'échelle actuelle (debounce déjà en place sur la recherche et l'auto-save).
    - Statut : Non modifié — aucun problème de performance réel constaté à l'échelle actuelle des données ; une optimisation (pagination/virtualisation, index de recherche) serait prématurée sans preuve d'un ralentissement réel. À reconsidérer si le volume d'activités grossit significativement (plusieurs milliers d'entrées).

--------------------------------------------------------------------------------
4. TESTS
--------------------------------------------------------------------------------
[x] Étendre la couverture de tests aux fonctions pures à fort risque
    - Problème : Seulement 29 tests existaient, couvrant 4 fichiers sur 12. Les calculs financiers, la logique undo/redo/historique et les tarifs versionnés n'avaient aucun test.
    - Solution : 21 nouveaux tests ajoutés (50 au total) : calculs financiers (computeActivityFinancials — personnel, services, frais, taxes TPS/TVQ), détection de conflits de réservation (timeRangesOverlap, getReservationOccupiedRanges), diff d'historique (computeActivityDiff), et résolution de tarifs/salaires versionnés par date d'effet (getActivePricingGrid, getActiveSalaryRate, getFlattenedRoomTarifs).
    - Non couvert : backup.js (export/import, IndexedDB, File System Access API) n'a pas de test — ses fonctions sont fortement couplées aux API navigateur (IndexedDB, FileReader, Blob) et nécessiteraient une dépendance de mocking (ex: fake-indexeddb) qui n'est pas dans le projet actuellement. À discuter si souhaité.
